  - release 브랜치는 ver 1.0 -> 2.0 진행 등 버전 업데이트 때 추가하기로 한 기능이 다 올라가는걸 기준으로 update 한다.
  - 버전 관리 방식 정리 필요
2. 브랜치 보호 전략
  - master에 머지 할 수 있는 브랜치는 develop, hotfix만
  - develop에 머지 할 수 있는 브랜치는 base만
  - base에 머지 할 수 있는 브랜치는 feat, fix만
3. BE, KOTLIN, SWIFT 별 git을 따로 만들지
  - 모노레포 장점 : API 명세 변경등 관리를 하나의 커밋으로 관리할 수 있어 흐름 파악이 용이, CI/CD 파이프라인이나 보안 정책을 통일 적용하기에 용이
  - 모노레포 단점 : 프로젝트 규모가 커지면 체크아웃 속도 느려지고 CI 설정이 복잡해진다.
  - 멀티레포 장점 : 프로젝트 빌드 도구별 충돌할 일이 없다, 협업시 혼선이 적다, 각 레포 별 히스토리가 명확하다, 각 언어와 프레임워크에 최적화된 전략을 적용할 수 있다.
  - 모노레포 단점 : API 변경 시 각각 작업을 해야한다. 각 저장소 별로 CI/CD 설정을 반복 세팅해야 한다.

## merge 컨벤션

1. Merge (일반 병합)
  가장 기본적인 방식, 두 브랜치의 변경 사항을 통합할 때 새로운 Merge Commit을 생성한다.

  - 특징: 브랜치가 나뉘고 합쳐지는 모든 히스토리가 그대로 남는다.
  - 장점: 작업의 맥락과 과정이 상세히 기록된다.
  - 단점: 팀원이 많아질 경우 커밋 그래프가 매우 복잡해질 수 있다.

2. Rebase (재배치)
  기능 브랜치의 시작점을 최신 마스터(또는 메인) 브랜치 끝으로 옮긴다.

  - 특징: 히스토리를 한 줄로 깔끔하게 정렬. 메인 브랜치에서 처음부터 작업한 것처럼 보인다.
  - 장점: 커밋 로그가 깨끗하여 프로젝트 흐름을 파악하기 쉽다.
  - 단점: 이미 원격 저장소에 Push된 커밋을 Rebase하면 히스토리가 꼬여 협업 시 위험할 수 있다.

3. Squash (압축 병합)
  여러 개의 커밋을 단 하나의 커밋으로 합쳐서 병합하는 방식.

  - 특징: 기능 브랜치에서 진행했던 수많은 자잘한 커밋들을 하나로 뭉쳐서 메인 브랜치에 붙인다.
  - 장점: 메인 브랜치에는 "기능 구현 완료"와 같은 큰 단위의 커밋만 남으므로 관리가 매우 용이하다.
  - 단점: 작업 중 발생했던 세부적인 수정 과정(로그)은 사라지게 된다.

결론 : merge로 진행

## commit message 컨벤션

```
타입: 제목  

내용
```

### 1. 타입

| 분류 | 타입 | 설명 |
|------|------|------|
| 기능 | `feat` | 기능 추가 |
| | `fix` | 오류 수정 |
| | `design` | 디자인 수정 |
| 개선 | `style` | 코드 포맷팅 |
| | `refact` | 코드 리팩토링 |
| | `comment` | 주석 등 문구 수정 |
| 기타 | `docs` | 문서 수정 |
| | `chore` | 빌드 작업 등 |
| | `rename` | 파일·폴더 이름 수정 |
| | `remove` | 파일·폴더 삭제 |

### 2. 제목

- 한글로 작성
- 개조식 구문 (서술형 작성 X)
- 마침표 및 특수기호 사용 X
- 최대한 간결하고 가독성 좋게

### 3. 내용

- How 보다 **What + Why** 중심으로 작성
- 작성 방식
  목록화
    ```
    - 내용1
    - 내용2
    - 내용3
    ```
    → 장점 : 가독성이 좋다, 추가 or 개선한 기능을 한눈에 보기 좋다.

### 목록화 예시
```
feat: 작곡 페이지 개발

- 작곡 페이지 UI/UX 개선
- 재생, 일시정지, 정지 버튼 추가
```

→ 결론 : 목록화로 작성

## 이슈관리

  ### 이슈 작성하는방법

  1. Issues > New Issue
  2. Add a title에 이슈 이름 작성 (작업 내용 간단히)
  3. Add a description에 이슈 내용 작성 (작업 내용 목록화)
  4. Assignees 에 담당자 지정
  5. Labels에 해당 작업 태그 지정
  6. Create
  7. 생성된 이슈번호로 브랜치, 커밋 메시지 관리

  ### 이슈 작성 기준
  - feat : 오프라인 회의 때 기간 동안 추가할 기능을 선정해 이슈 생성
  - fix : 오프라인 회의 때 기간 동안 수정할 오류를 선정해 이슈를 생성하거나 개발자가 필요에 의해 이슈 생성
  - docs : 오프라인 회의 떄 기간 동안 작성할 문서를 선정해 이슈를 생성하거나 개발자가 필요에 의해 이슈 생성
  - chore : 오프라인 회의 때 기간 동안 진행할 작업을 선정해 이슈 생성

  ### Labels 종류

  | 타입 | 설명 |
  |------|------|
  | `fix` | 오류 개선 |
  | `docs` | 문서 작업 |
  | `feat` | 기능 추가 |
  | `chore` | 빌드 작업 |
    
  ### 이슈 작성 예시

  ```
  title : 메인 페이지 작성
  description : - 로고 이미지 배치
                - 메인 페이지 CSS 작성
  Assignees : kkkmmh
  Labels : feat
  ```
