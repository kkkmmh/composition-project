## branch 컨벤션

```
master → hotfix
   ↓
develop (default) → fix
   ↓           
feature   
```

> 브랜치 네이밍 : 작업유형/기능명(케밥케이스)
>
> ```
> feat/login-page
> feat/composition-page
> fix/login-page
> hotfix/login-page
> ```
>
> ※ 추후 지라 등 업데이트 시 양식 변경 가능

**고려할 점**

1. release 사용 여부
  - release : 이번에 출시할 버전을 준비하는 보조 브랜치, develop 브랜치에서 개발한 내용을 해당 브랜치로 옮겨와 QA 및 테스트를 진행함
  - 내 생각 : 초기 개발 단계 진행중에는 사용 X, 정식 기능이 다 추가된 후 실제 배포 전 브렌치 파서 사용하는게 좋을 듯 싶다.
2. 브랜치 보호 전략
  - master에 머지 할 수 있는 브랜치는 develop, hotfix만 → master 머지 권한은 배포를 해야하는 승호형 or git을 관리하는 나 둘중 한명에게 줄 생각
  - develop에 머지 할 수 있는 브랜치는 feature, fix만 → develop 머지 권한은 세명 모두에게 있다.
  - 만약 모노레포를 하게 된다면 → feature 브랜치를 BE, Kotlin, Swift 3개로 나눈 후 관리할 생각이다.
3. BE, KOTLIN, SWIFT 별 git을 따로 만들지
  - 모노레포 장점 : API 명세 변경등 관리를 하나의 커밋으로 관리할 수 있어 흐름 파악이 용이, CI/CD 파이프라인이나 보안 정책을 통일 적용하기에 용이
  - 모노레포 단점 : 프로젝트 규모가 커지면 체크아웃 속도 느려지고 CI 설정이 복잡해진다.
  - 멀티레포 장점 : 프로젝트 빌드 도구별 충돌할 일이 없다, 협업시 혼선이 적다, 각 레포 별 히스토리가 명확하다, 각 언어와 프레임워크에 최적화된 전략을 적용할 수 있다.
  - 모노레포 단점 : API 변경 시 각각 작업을 해야한다. 각 저장소 별로 CI/CD 설정을 반복 세팅해야 한다.
  - 내 생각 : 모노레포가 편할 것 같긴한데 CI/CD랑도 연결되는 이야기 이니 함께 고민해봐야할듯

## merge 컨벤션

1. Merge (일반 병합)
  가장 기본적인 방식, 두 브랜치의 변경 사항을 통합할 때 새로운 Merge Commit을 생성한다.

  - 특징: 브랜치가 나뉘고 합쳐지는 모든 히스토리가 그대로 남는다.
  - 장점: 작업의 맥락과 과정이 상세히 기록된다.
  - 단점: 팀원이 많아질 경우 커밋 그래프가 매우 복잡해질 수 있다.

2. Rebase (재배치)
  기능 브랜치의 시작점을 최신 마스터(또는 메인) 브랜치 끝으로 옮긴다.

  - 특징: 히스토리를 한 줄로 깔끔하게 정렬. 메인 브랜치에서 처음부터 작업한 것처럼 보인다.
  - 장점: 커밋 로그가 깨끗하여 프로젝트 흐름을 파악하기 쉽다.
  - 단점: 이미 원격 저장소에 Push된 커밋을 Rebase하면 히스토리가 꼬여 협업 시 위험할 수 있다.

3. Squash (압축 병합)
  여러 개의 커밋을 단 하나의 커밋으로 합쳐서 병합하는 방식.

  - 특징: 기능 브랜치에서 진행했던 수많은 자잘한 커밋들을 하나로 뭉쳐서 메인 브랜치에 붙인다.
  - 장점: 메인 브랜치에는 "기능 구현 완료"와 같은 큰 단위의 커밋만 남으므로 관리가 매우 용이하다.
  - 단점: 작업 중 발생했던 세부적인 수정 과정(로그)은 사라지게 된다.

→ 그냥 기본 merge 쓰고싶다..

## commit message 컨벤션

```
타입: 제목

내용
```

### 1. 타입

| 분류 | 타입 | 설명 |
|------|------|------|
| 기능 | `feat` | 기능 추가 |
| | `fix` | 오류 수정 |
| | `design` | 디자인 수정 |
| 개선 | `style` | 코드 포맷팅 |
| | `refact` | 코드 리팩토링 |
| | `comment` | 주석 등 문구 수정 |
| 기타 | `docs` | 문서 수정 |
| | `chore` | 빌드 작업 등 |
| | `rename` | 파일·폴더 이름 수정 |
| | `remove` | 파일·폴더 삭제 |

### 2. 제목

- 한글로 작성
- 개조식 구문 (서술형 작성 X)
- 마침표 및 특수기호 사용 X
- 최대한 간결하고 가독성 좋게

### 3. 내용

- How 보다 **What + Why** 중심으로 작성
- 고려 중인 작성 방식
  1. 목록화
     ```
     - 내용1
     - 내용2
     - 내용3
     ```
     → 장점 : 가독성이 좋다, 추가 or 개선한 기능을 한눈에 보기 좋다.
  2. 문장화
     ```
     @@@한 이슈로 인한 @@@ 작업 진행하였으며 $$$기능 추가를 위한 백엔드 개발 추후 개선 예정
     ```
     → 장점 : 개발 내용을 상세하게 적어 나중에 다시 확인할때 편하다.


### 목록화 예시
```
feat: 작곡 페이지 개발

- 작곡 페이지 UI/UX 개선
- 재생, 일시정지, 정지 버튼 추가
```

### 문장화 예시
```
feat: 작곡 페이지 개발

재생, 일시정지, 정지 버튼 페이지 상단에 추가작업 진행하였으며 전반적인 작곡 페이지 UI/UX 개선
```

→ 목록화로 commit message 작성하고, 개발일지? 같은걸 따로 작성하는게 좋을것 같다.
